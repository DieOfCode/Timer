# Учебный проект «Таймер» на Android Views/XML

Целевая структура экранов и границы ответственности зафиксированы в
[`ARCHITECTURE.md`](ARCHITECTURE.md).

Расширенный урок про системные сообщения, запуск компонентов и `PendingIntent`
находится в [`lessons/intent.md`](lessons/intent.md).

Курс по Fragment разделён на шесть коротких частей с отдельной практикой.
Оглавление находится в [`lessons/fragments.md`](lessons/fragments.md).

Этот курс рассчитан на первый Android-проект на Kotlin. Мы не будем использовать
Jetpack Compose: весь интерфейс создаётся в XML, а Kotlin отвечает за состояние и
поведение приложения.

## Что получится в конце

Пользователь сможет:

- задать часы, минуты и секунды;
- запустить обратный отсчёт;
- поставить его на паузу и продолжить;
- сбросить таймер;
- повернуть экран без потери текущего состояния;
- свернуть приложение и получить уведомление по окончании времени.

Минимальные состояния экрана:

```text
READY -> RUNNING -> PAUSED -> RUNNING
  ^          |          |
  +----------+----------+
             RESET

RUNNING -> FINISHED -> READY
```

Не пытайтесь написать всё сразу. После каждого этапа запускайте приложение и
проверяйте только новую возможность.

## Модуль 0. Минимум Kotlin

### Изучить

- `val` и `var`, типы `Int`, `Long`, `Boolean`, `String`;
- условия `if` и `when`;
- функции и параметры;
- классы, свойства и методы;
- nullable-типы (`String?`), безопасный вызов `?.`;
- лямбды — они понадобятся обработчикам нажатий;
- целочисленное деление и остаток `%`.

### Мини-практика

Напишите отдельно от Android две чистые функции:

```kotlin
fun toMillis(hours: Int, minutes: Int, seconds: Int): Long {
    return (hours * 3_600L + minutes * 60L + seconds) * 1_000L
}

fun formatTime(milliseconds: Long): String {
    val totalSeconds = milliseconds / 1_000L
    val hours = totalSeconds / 3_600L
    val minutes = (totalSeconds % 3_600L) / 60L
    val seconds = totalSeconds % 60L
    return "%02d:%02d:%02d".format(hours, minutes, seconds)
}
```

Почему в вычислениях используется `Long`: миллисекунды быстро выходят за удобный
диапазон `Int`, а Android API времени обычно работают с `Long`.

### Проверка

- `toMillis(0, 1, 30)` возвращает `90_000`;
- `formatTime(90_000)` возвращает `00:01:30`;
- `formatTime(3_661_000)` возвращает `01:01:01`.

## Модуль 1. Как устроено Android-приложение

Откройте существующий проект и найдите:

- `app/src/main/java/com/example/timer/MainActivity.kt` — точка входа экрана;
- `app/src/main/res/layout/activity_main.xml` — разметка экрана;
- `app/src/main/res/values/strings.xml` — пользовательские строки;
- `app/src/main/res/values/colors.xml` и `themes.xml` — оформление;
- `app/src/main/AndroidManifest.xml` — компоненты и разрешения;
- `app/build.gradle.kts` — настройки модуля и зависимости.

### Главные понятия

**Activity** — объект, управляющий экраном. `onCreate()` вызывается при создании
Activity. Вызов `setContentView(R.layout.activity_main)` превращает XML-ресурс в
дерево объектов `View`.

**Ресурсы** — строки, цвета, размеры, изображения и разметка вне Kotlin-кода.
Android выбирает подходящий вариант ресурса для языка, темы и размера экрана.

**Manifest** сообщает системе, какие компоненты и возможности есть у приложения.

### Подробно: что такое Activity

`Activity` — не сам XML-экран и не отдельный визуальный элемент. Это Android-
компонент, который:

- получает lifecycle-события от системы;
- создаёт и размещает иерархию `View`;
- обрабатывает действия пользователя и системные события;
- предоставляет `Context`, через который доступны ресурсы и системные сервисы.

Когда приложение запускает `MainActivity`, система сама создаёт экземпляр класса
и вызывает его методы. Поэтому Activity не запускают через `MainActivity()` и не
хранят как обычный объект.

Упрощённая последовательность создания экрана:

```text
Android читает Manifest
  -> создаёт MainActivity
  -> вызывает onCreate(savedInstanceState)
  -> Activity получает XML-разметку
  -> LayoutInflater создаёт объекты View
  -> setContentView размещает корневую View в окне Activity
  -> вызываются onStart() и onResume()
```

Один экземпляр Activity живёт только до `onDestroy()`. При повороте экрана
система обычно уничтожает старый экземпляр и создаёт новый. Поэтому Activity не
подходит для постоянного хранения состояния таймера.

### Подробно: XML, LayoutInflater и inflate()

Файл `activity_main.xml` — это описание интерфейса, а не готовый экран. Пока XML
не прочитан, объектов `ConstraintLayout`, `TextView` и `Button` в памяти нет.

`LayoutInflater` читает XML и создаёт соответствующее дерево Kotlin/Java-объектов:

```text
activity_main.xml
  <ConstraintLayout>
    <TextView />
    <Button />
  </ConstraintLayout>

            inflate()
                |
                v

ConstraintLayout object
  |- TextView object
  `- Button object
```

Слово **inflate** можно понимать как «развернуть описание»: компактный XML
превращается в полноценную иерархию объектов `View` в оперативной памяти.

Самый явный вариант выглядит так:

```kotlin
val rootView = layoutInflater.inflate(
    R.layout.activity_main,
    null,
    false
)
setContentView(rootView)
```

Но для Activity обычно пишут короче:

```kotlin
setContentView(R.layout.activity_main)
```

Внутри происходит похожая работа: Activity использует inflater и прикрепляет
полученную корневую `View` к своему окну.

### Три параметра inflate()

Общая форма:

```kotlin
inflater.inflate(layoutResource, parent, attachToRoot)
```

- `layoutResource` — какой XML нужно развернуть;
- `parent` — будущий родитель корневой `View`; он помогает правильно создать
  `LayoutParams`;
- `attachToRoot` — нужно ли сразу добавить созданную `View` внутрь `parent`.

Передавать `null` в `parent` удобно для первого эксперимента, но в переиспользуемых
элементах это может привести к неправильным параметрам разметки. Типичные случаи:

```kotlin
// Activity: View Binding создаёт root, Activity прикрепляет его к окну позже.
val binding = ActivityMainBinding.inflate(layoutInflater)
setContentView(binding.root)

// Fragment: контейнер нужен для LayoutParams, но прикрепление выполняет FragmentManager.
val binding = FragmentTimerBinding.inflate(inflater, container, false)
return binding.root

// Элемент списка: RecyclerView сам прикрепит ViewHolder к себе.
val binding = ItemTimerBinding.inflate(inflater, parent, false)
```

Если передать `attachToRoot = true`, inflater сразу добавит новую `View` в
`parent`. Если после этого контейнер или фреймворк попробует добавить её повторно,
приложение получит ошибку о том, что у View уже есть родитель.

### Как View Binding связан с inflate()

View Binding не отменяет inflation. Вызов:

```kotlin
val binding = ActivityMainBinding.inflate(layoutInflater)
```

одновременно:

1. разворачивает `activity_main.xml` в объекты `View`;
2. создаёт `ActivityMainBinding`;
3. помещает в binding типобезопасные ссылки на View с `id`.

После этого:

```kotlin
binding.root          // корневая View из XML
binding.timerText     // TextView с id="timerText"
binding.startButton   // кнопка с id="startButton"
```

Есть и другой метод:

```kotlin
val binding = ActivityMainBinding.bind(alreadyInflatedView)
```

`bind()` не читает XML заново. Он принимает уже созданную иерархию и только
находит в ней необходимые View. Для нашей Activity используйте `inflate()`, потому
что в момент `onCreate()` дерево ещё не создано.

### Практический эксперимент с inflate()

1. Временно создайте экран через `setContentView(R.layout.activity_main)`.
2. Найдите `TextView` через `findViewById` и измените его текст.
3. Затем замените этот код на `ActivityMainBinding.inflate(layoutInflater)` и
   `setContentView(binding.root)`.
4. Измените тот же текст через `binding.timerText`.
5. Поставьте breakpoint после `inflate()` и изучите `binding.root` в Debugger.

Результат на экране одинаковый. Отличается способ получения ссылок: View Binding
проверяет их типы на этапе компиляции и делает код понятнее.

## Модуль 3. View Binding и события

View Binding создаёт типобезопасную ссылку на каждую `View` с `id` и избавляет от
большинства вызовов `findViewById`.

### Шаг 1. Включить View Binding

В `android`-блоке файла `app/build.gradle.kts`:

```kotlin
buildFeatures {
    viewBinding = true
}
```

После синхронизации Gradle для `activity_main.xml` появится класс
`ActivityMainBinding`.

### Шаг 2. Подключить разметку

```kotlin
private lateinit var binding: ActivityMainBinding

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    binding = ActivityMainBinding.inflate(layoutInflater)
    setContentView(binding.root)
}
```

Существующую обработку системных отступов можно оставить, обращаясь к
`binding.root`.

### Шаг 3. Обработать нажатие

```kotlin
binding.startButton.setOnClickListener {
    val minutes = binding.minutesInput.text.toString().toIntOrNull() ?: 0
    binding.timerText.text = formatTime(toMillis(0, minutes, 0))
}
```

### Валидация

Перед стартом проверьте:

- все пустые поля считаются нулём;
- минуты и секунды находятся в диапазоне `0..59`;
- общее время больше нуля;
- слишком большое значение не переполняет вычисления.

Ошибка должна быть видна возле поля (`TextInputLayout.error`) или в коротком
сообщении, а не приводить к падению приложения.

### Готово, если

по нажатию «Старт» введённое время преобразуется и отображается в формате
`HH:MM:SS`, а неверный ввод получает понятное сообщение.

## Модуль 4. Обратный отсчёт на открытом экране

Для первой рабочей версии используйте `CountDownTimer`:

```kotlin
private var countDownTimer: CountDownTimer? = null
private var remainingMillis = 0L

private fun startTimer(durationMillis: Long) {
    countDownTimer?.cancel()

    countDownTimer = object : CountDownTimer(durationMillis, 1_000L) {
        override fun onTick(millisUntilFinished: Long) {
            remainingMillis = millisUntilFinished
            renderTime()
        }

        override fun onFinish() {
            remainingMillis = 0L
            renderTime()
            renderFinishedState()
        }
    }.start()
}
```

### Важная идея

Не делайте число на экране источником состояния. `TextView` только показывает
`remainingMillis`. Данные меняются в Kotlin, затем отдельная функция `render...()`
перерисовывает интерфейс.

### Реализовать

- `startTimer()`;
- `pauseTimer()` — отменяет `CountDownTimer`, но сохраняет остаток;
- `resumeTimer()` — запускает новый отсчёт от остатка;
- `resetTimer()` — отменяет отсчёт и возвращает исходное состояние;
- блокировку полей ввода во время работы.

### Не делать

- `Thread.sleep()` на главном потоке — интерфейс зависнет;
- бесконечный цикл для обновления текста;
- создание нового таймера без отмены предыдущего;
- хранение единственной копии времени в тексте `TextView`.

### Самопроверка

- повторное нажатие «Старт» не создаёт два параллельных отсчёта;
- пауза действительно останавливает число;
- продолжение идёт с сохранённого остатка;
- сброс возвращает интерфейс в `READY`;
- на нуле показывается `00:00:00`, а не отрицательное значение.

## Модуль 5. Жизненный цикл и состояние

Сейчас поворот устройства пересоздаёт `MainActivity`; поле класса и объект
`CountDownTimer` теряются. Это ожидаемое поведение Android.

### Сначала проведите эксперимент

Добавьте Logcat-сообщения в `onCreate`, `onStart`, `onResume`, `onPause`, `onStop`
и `onDestroy`. Запустите таймер, поверните экран, сверните приложение и вернитесь.
Запишите последовательности callbacks.

### Правильная модель времени

Не сохраняйте только «осталось 37 секунд»: пока Activity пересоздаётся, настоящее
время продолжает идти. Для работающего таймера храните конечный момент:

```kotlin
endTimeMillis = SystemClock.elapsedRealtime() + remainingMillis
remainingMillis = (endTimeMillis - SystemClock.elapsedRealtime()).coerceAtLeast(0L)
```

`elapsedRealtime()` монотонен и не меняется, если пользователь исправляет часы
устройства.

### Разделение ответственности

Создайте:

```text
MainActivity
  - получает события View
  - наблюдает за состоянием
  - рисует экран

TimerViewModel
  - хранит состояние таймера
  - start / pause / resume / reset
  - считает оставшееся время

TimerUiState
  - status
  - remainingMillis
  - первоначальная длительность
  - endTimeMillis для работающего таймера
```

Подключите `lifecycle-viewmodel-ktx` и создайте `TimerViewModel : ViewModel()`.
Для первого прохода можно наблюдать `LiveData`; если Kotlin уже понятен — выбрать
`StateFlow` и собирать его с учётом lifecycle.

### Что должно переживать разные события

| Событие | Механизм |
|---|---|
| Поворот экрана | `ViewModel` |
| Убийство процесса системой | `SavedStateHandle` или сохранённый `endTimeMillis` |
| Закрытие приложения пользователем | Решение продукта: сброс либо постоянное хранение |
| Перезагрузка телефона | Отдельное усложнение, не входит в MVP |

### Готово, если

- при повороте таймер продолжает идти;
- после ухода на другой экран и возврата показывается корректный остаток;
- Activity не содержит бизнес-логику расчёта времени;
- `CountDownTimer` не удерживает уничтоженную Activity.

## Модуль 6. Уведомления

Сначала научитесь показывать тестовое уведомление по кнопке, и только потом
соединяйте его с таймером.

### Изучить и реализовать

1. Добавить разрешение `POST_NOTIFICATIONS` в Manifest.
2. Создать `NotificationChannel` при запуске приложения (Android 8+).
3. На Android 13+ запросить разрешение во время выполнения.
4. Создать уведомление через `NotificationCompat.Builder`.
5. Добавить `PendingIntent`, открывающий `MainActivity` по нажатию.
6. Если разрешение отклонено, приложение не должно падать.

Разрешение лучше запрашивать в понятном контексте — когда пользователь впервые
запускает таймер, а не сразу после открытия приложения.

### Готово, если

- уведомление видно в шторке;
- нажатие открывает приложение;
- повторное уведомление не создаёт бесконечную пачку карточек;
- отказ в разрешении обрабатывается спокойно.

## Модуль 7. Надёжное завершение в фоне

`CountDownTimer` удобен для обновления открытого экрана, но не является гарантией
фонового оповещения: процесс приложения может быть уничтожен. Поэтому финальная
версия использует два механизма:

```text
Открытый экран: CountDownTimer обновляет текст раз в секунду
Фон/закрытый экран: AlarmManager будит BroadcastReceiver в момент окончания
```

### Компоненты

**AlarmScheduler** создаёт и отменяет системный alarm с уникальным
`PendingIntent`.

**TimerExpiredReceiver : BroadcastReceiver** получает системное событие и
показывает уведомление. Зарегистрируйте receiver в Manifest; он не должен быть
экспортирован для других приложений.

**Хранилище состояния** сохраняет минимум: статус, исходную длительность и момент
окончания. Для такого небольшого проекта достаточно `SharedPreferences`; позже
можно изучить DataStore.

### Точный или неточный alarm

Для настоящего пользовательского таймера точность — основная функция. Android
позволяет приложениям таймеров использовать `USE_EXACT_ALARM`, но публикация с
этим разрешением должна соответствовать правилам магазина. В учебной версии
обязательно разберите альтернативу `SCHEDULE_EXACT_ALARM`: проверка
`canScheduleExactAlarms()`, переход в системные настройки за специальным доступом
и корректное ухудшение поведения при отказе.

Не используйте `WorkManager` как секундомер: он предназначен для гарантированной
отложенной работы, но не для срабатывания секунда в секунду.

### Алгоритм запуска

```text
1. Проверить ввод и разрешение на уведомления.
2. Вычислить endTime = elapsedRealtime + duration.
3. Сохранить состояние.
4. Запланировать системный alarm.
5. Запустить экранный CountDownTimer.
```

### Алгоритм паузы/сброса

```text
1. Отменить экранный CountDownTimer.
2. Отменить тот же PendingIntent в AlarmManager.
3. Сохранить остаток (pause) или очистить состояние (reset).
4. Перерисовать экран.
```

### Готово, если

- таймер завершается при открытом приложении;
- уведомление приходит после сворачивания;
- уведомление приходит при выключенном экране;
- пауза и сброс отменяют запланированный alarm;
- после возвращения приложение вычисляет остаток по конечному моменту;
- нет двойного уведомления от `CountDownTimer` и `BroadcastReceiver`.

Перезагрузка устройства — бонусное задание: receiver на `BOOT_COMPLETED` может
восстановить alarm из постоянного состояния. Сначала добейтесь идеальной работы
MVP без этой функции.

## Модуль 8. Тесты и качество

### Unit-тесты без Android

Вынесите чистые расчёты из Activity/ViewModel и проверьте:

- преобразование часов, минут и секунд в миллисекунды;
- форматирование `0`, одной секунды, минуты, часа;
- невозможность отрицательного остатка;
- переходы `READY -> RUNNING -> PAUSED -> RUNNING -> FINISHED`.

### Ручной чек-лист

- [ ] Пустой ввод.
- [ ] Все три поля равны нулю.
- [ ] Секунды или минуты больше 59.
- [ ] Очень большое число часов.
- [ ] Быстрые повторные нажатия на кнопки.
- [ ] Поворот экрана в состояниях `READY`, `RUNNING`, `PAUSED`.
- [ ] Сворачивание на 10–20 секунд и возврат.
- [ ] Выключение экрана до завершения.
- [ ] Разрешение на уведомления выдано и отклонено.
- [ ] Доступ к точным alarm выдан и отклонён.
- [ ] Смена системного времени не ломает остаток.
- [ ] Тёмная тема и увеличенный системный шрифт.

### Definition of Done

Проект завершён, если:

1. Он собирается без ошибок и предупреждений, созданных вашим кодом.
2. Все строки находятся в ресурсах.
3. Бизнес-логика не зависит от `TextView` и `EditText`.
4. Поворот экрана не сбрасывает состояние.
5. Фоновое завершение даёт одно уведомление.
6. Пауза и сброс отменяют системный alarm.
7. Основные расчёты покрыты unit-тестами.

## Как проходить курс эффективно

Для каждого занятия используйте цикл:

```text
Прочитать понятие (20%)
  -> написать маленький пример (20%)
  -> применить в таймере (50%)
  -> сломать и проверить крайние случаи (10%)
```

После занятия сделайте короткий commit. Не копируйте финальный проект целиком:
цель курса — понять, почему следующий слой появляется именно сейчас.

## Контрольные вопросы

К завершению проекта вы должны уметь ответить:

1. Чем XML-разметка отличается от объекта `View` во время выполнения?
2. Почему строки и цвета хранятся в ресурсах?
3. Что происходит с Activity при повороте экрана?
4. Почему `ViewModel` не должен хранить ссылку на Activity или её View?
5. Почему остаток лучше вычислять от конечного момента, а не уменьшать вручную?
6. Чем экранный `CountDownTimer` отличается от системного `AlarmManager`?
7. Зачем нужны `NotificationChannel`, runtime permission и `PendingIntent`?
8. Почему `Thread.sleep()` нельзя вызывать на главном потоке?
9. Что должно произойти, если пользователь отказал в разрешении?
10. Какие части приложения можно тестировать обычным unit-тестом?

Если на эти вопросы есть уверенный ответ и весь чек-лист пройден, задача не
просто выполнена — вы действительно освоили базовый цикл разработки Android
приложения на Views/XML.
